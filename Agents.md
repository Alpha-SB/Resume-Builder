# AGENTS.md — CSC3100 Final Project (Resume Builder)

This file defines the coding, architecture, accessibility, API, AI, and documentation rules for this project.
These rules are based on the class-wide standards provided by the instructor and further specialized for the CSC3100 Final Resume Builder project.

---

## 1) Project Overview

This application is a local-first Resume Builder designed to help users create, store, tailor, preview, and print resumes.

### Required project goals
- Use **HTML/CSS/JavaScript** on the frontend (no React or other frontend frameworks)
- Use **Node.js + Express** for backend REST APIs
- Use **SQLite** for application data storage
- Build as a **single page application (SPA)** with one primary `index.html`
- Store reusable user data (experience, bullet points, skills, certifications, awards, education)
- Allow users to generate tailored resumes by selecting stored items
- Integrate a **Generative AI API** to review and suggest improvements to user-entered content
- Support both:
  - a **web/digital preview**
  - a **print-friendly layout** for PDF generation
- Keep all third-party libraries **local to the project** (no CDNs)

---

## 2) Core Technology Rules

### Frontend
- Use **plain HTML, CSS, and JavaScript only**
- **Do NOT use React, Vue, Angular, Svelte, or other frontend frameworks**
- The application must behave as a **single page application**
- There should be one primary `index.html` that dynamically shows/hides views or loads/unloads DOM sections

### CSS / Styling
- Prefer **Bootstrap 5+** for layout, forms, spacing, and responsive design
- A **Bootswatch** theme may be used if desired
- Use **Bootstrap utility classes first**
- Avoid excessive custom CSS
- Custom CSS is allowed only when Bootstrap cannot reasonably achieve the required design
- Avoid inline styles unless absolutely necessary
- A dedicated `print.css` file should be used for print/PDF layout

### Rich Text
- **QuillJS** may be used for limited rich text areas such as:
  - professional summary
  - notes
  - AI suggestion display/editing
- Avoid using Quill for all resume bullet points unless there is a clear reason
- Prefer structured text fields for resume bullet content to keep print output consistent

### Backend
- Use **Node.js + Express**
- Do **NOT** use MVC or SSR frameworks
- Do **NOT** use server-side rendered templates such as EJS, Pug, Handlebars, etc.
- Serve static frontend assets from Express
- The backend should expose **RESTful JSON APIs only**

### Database
- Use **SQLite** as required by the project
- Prefer parameterized queries / prepared statements only
- Never concatenate raw user input into SQL queries
- Keep schema files in `/db`
- Keep migrations or versioned schema updates in a dedicated `/db/migrations` folder if used

### Desktop Packaging (Optional / Extra Credit)
- ElectronJS may be used to wrap the completed web application after the web version is fully functional
- Electron should be added **after** the browser-based MVP is complete
- If Electron is used:
  - enable `contextIsolation`
  - use a `preload.js`
  - use `contextBridge` for safe IPC exposure
  - do not expose full `ipcRenderer` directly to the renderer

## 3) Coding Conventions

### Naming
- Use **Hungarian Notation** for variable naming where applicable, consistent with class expectations
- Use **camelCase** for variables and function names

Examples:
- `strUserName`
- `intResumeId`
- `arrSkills`
- `objResponse`
- `blnIsValid`

### JavaScript
- Prefer **ES6+**
- Use:
  - `const` by default
  - `let` when reassignment is required
- Prefer **async/await** over `.then()` when working with asynchronous JavaScript
- Prefer native Web APIs over additional dependencies
- Avoid jQuery unless specifically required or previously approved by instructor
- Keep frontend code modular and split into multiple files
- Do **NOT** place large JavaScript blocks directly in `index.html`

### Comments
- Provide **verbose and beginner-friendly comments**
- Comment:
  - application flow
  - non-obvious logic
  - API interactions
  - AI request/response handling
  - print layout logic
  - any code generated or significantly assisted by AI
- Any code substantially generated by AI should include comments explaining what it does in plain language

## 4) Project Structure Rules

### Required structure expectations
- Node.js entry point must be:
  - `server.js`

### Recommended folders
- `/public` for frontend assets
- `/public/js` for frontend JavaScript modules
- `/public/css` for stylesheets
- `/public/vendor` for locally stored third-party libraries
- `/db` for SQLite database, schema, and migrations
- `/api` for route registration and API modules
- `/services` for business logic / AI integration helpers
- `/docs` for project and AI documentation

### Routing
- All API routes should be organized under:
  - `/api/...`

Example:
- `/api/profile`
- `/api/education`
- `/api/experience`
- `/api/skills`
- `/api/certifications`
- `/api/awards`
- `/api/resumes`
- `/api/ai`
- `/api/settings`

> Note: The original class file mentions `/api/routing`. For this project, the important requirement is that all APIs live under `/api`.  
> If your teacher specifically expects a literal `/api/routing` folder, keep that folder name. Otherwise, `/api/routes` or `/api` is cleaner and more conventional.

## 5) API Requirements

### General
- All API routes must be **RESTful**
- All API responses should be JSON
- Use proper HTTP status codes for success and failure
- All user inputs must be validated before processing

### Route method rules
- **GET / SELECT**
  - Use query strings or URL parameters as appropriate
  - Return JSON arrays for collection endpoints
  - Return a JSON object for single-resource endpoints if needed
- **POST / CREATE**
  - Accept JSON request bodies
- **PUT / UPDATE**
  - Use `PUT` instead of `PATCH` per class convention
- **DELETE**
  - Use URL parameters for resource identifiers

### Validation
- Validate:
  - required fields
  - data types
  - string lengths
  - enum-like values
  - empty strings
- Sanitize user-entered rich text or HTML before storing or rendering
- Never trust AI output as already safe for direct HTML rendering

## 6) Security Rules

### Credentials / Secrets
- Do **NOT** hardcode credentials
- Development secrets must be stored in `.env`
- `.env` must be listed in `.gitignore`
- Provide a `.env.example` file for setup instructions

### AI API Keys
- The application must support a **user-provided Gemini API key**
- The project must **NOT** ship with a real API key embedded in source code
- During development, your personal key may be stored in `.env`
- If the app allows saving a user key locally, clearly document:
  - where it is stored
  - that it remains local to the user’s machine
- Never commit real API keys to the public GitHub repository

### SQL
- Use prepared statements / parameterized queries only
- Never intermix user input directly into SQL queries

### Output Safety
- Sanitize any HTML rendered from:
  - user input
  - Quill content
  - AI output
- Never blindly inject AI output into the DOM with `innerHTML`

## 7) Accessibility Rules (High Priority)

### Required standards
- All UI must meet **WCAG 2.1+**
- Accessibility takes priority over visual style
- All forms must have:
  - proper `<label>` associations
  - ARIA labels when necessary
  - accessible validation messaging
- All images/icons that need description must include meaningful `alt` text
- Decorative images should use empty alt text where appropriate

### Lighthouse requirement
- The final project must achieve a **Lighthouse Accessibility score of 93 or higher**
- Accessibility testing should be performed throughout development, not only at the end
- Include a screenshot or documentation of the Lighthouse result in the submission

### Keyboard / Focus
- All interactive UI must be keyboard accessible
- Modals must manage focus correctly
- Avoid inaccessible custom controls when native elements are sufficient

## 8) Resume Builder Domain Rules

### Data model expectations
The application should store reusable resume content in structured form, including:
- profile/contact info
- education
- experience entries
- experience bullet points / responsibilities
- skills and/or skill categories
- certifications
- awards
- optionally projects

### Resume generation
- Users should be able to create one or more resume versions by selecting:
  - which jobs to include
  - which bullets to include
  - which skills/categories to include
  - which certifications/awards to include
- The resume preview should be generated from stored structured data, not hardcoded HTML

### Print / PDF
- The application must support:
  - on-screen resume preview
  - print-friendly resume layout
- Prefer using browser print (`window.print()`) and print CSS for PDF generation
- The print layout should:
  - remove non-resume UI
  - preserve readable spacing
  - avoid cut-off sections
  - use print-safe font sizing and margins

## 9) AI Integration Rules (Project-Specific)

### Required AI behavior
The application must use a **Generative AI API** to review and provide suggestions after users enter resume content.

### Preferred provider
- Primary provider for this project should be **Google Gemini**
- Use the free tier where practical
- The app should be designed around **user-supplied API keys**

### Allowed AI use cases
AI may be used for:
- improving resume bullet points
- suggesting stronger action verbs
- rewriting for clarity
- improving ATS-style phrasing
- suggesting what to quantify
- tailoring content to a pasted job description
- generating or improving professional summaries

### Forbidden AI behavior
AI must **NOT**:
- invent facts, employers, certifications, dates, or achievements
- fabricate metrics or numbers
- claim experience the user did not provide
- silently replace user content without showing the suggested changes first

### AI prompting rules
Prompts should instruct the model to:
- preserve factual accuracy
- never fabricate
- improve clarity and professionalism
- prefer concise resume language
- suggest quantification opportunities without inventing numbers
- return structured JSON when practical

### AI UX rules
- AI suggestions should be **reviewable by the user**
- The user should explicitly choose whether to:
  - accept
  - reject
  - edit
- Do not auto-overwrite user data without confirmation

### AI output handling
- Validate and sanitize AI output before rendering
- Prefer structured responses (JSON) over free-form text when possible
- Gracefully handle:
  - missing API key
  - API errors
  - rate limits
  - malformed AI responses

## 13) Decision Guidelines

When uncertain, prefer:
- simpler code
- maintainable structure
- explicit validation
- accessibility over visual novelty
- predictable print output over flashy formatting
- browser-first implementation before Electron packaging

### Important implementation order
1. Build the web app MVP first
2. Finish CRUD + AI + preview + print layout
3. Then add Electron only if the browser version is stable
